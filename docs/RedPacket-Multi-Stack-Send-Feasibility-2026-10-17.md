# 普通资源多堆组成一个红包：底层链路评估（2026-10-17）

## 用户目标与结论

普通资源（石块、化合燃料等）同类只显示一个商品行，选择的是总数量；来自多个物品堆时，仍创建一个逻辑红包。武器、护甲及类似需要区分个体的物品保留单件选择，不按普通资源汇总发送。

**地图普通资源多堆发送的基础链路已经存在，等价状态资源可以复用现有协议与领取方式。新的汇总列表尚未接通这个业务入口，因此当前 0.0.5 浏览候选的多来源项仍不能发送。跨库存记录和地图/库存混合来源不能视为一并完成。**

本次为静态链路评估和已有回归核验，未实施发送行为改动，未发布新版本。没有将现有实现中“选一种模板代表不同状态”的行为当作本次用户授权的状态转换规则。

## 逐段证据

| 链路 | 当前真实能力 | 本次所需修改/判断 |
|---|---|---|
| 列表 | `RedPacketItemChoice` 保存多个原选择项引用和总量；多来源项暂禁发送 | 普通资源商品行应能生成来源分配计划；装备/护甲保留个体，不能仅用 Def+品质代替个体身份 |
| 入口 | `RedPacketTab.selectedStack` 只有一个 `RedPacketAvailableItem`；后者可包裹包含多个 Thing 的 `StackedThings` | 需要把多个来源行中的物理 Thing 汇总为业务选择，而非把第一个来源指给现有入口 |
| 多堆预检 | `RedPacketStackTemplate.PreparePhysical` 接受多个 Thing 和目标总数，复核状态、可堆叠性，选足来源；`CaptureCount` 构造总数量模板 | 普通资源的状态兼容策略需明确，选择后发送前复核；不改原始物品归属来实现列表合并 |
| 取物 | Trade 的 `StackedThings.PopSelectedWithOrigins` 逐堆扣取，最后一堆可 SplitOff，保留原地图/位置等恢复信息 | 可复用；不能用循环多次调用“发送”代替这一步 |
| 创建 | `TrySendPacket` 每次生成一个 PacketId、一个 RedPacket，把选中实物放入同一个 StoredThings 集合，再调用一次 AddLocalPacket | 支持多堆但一个逻辑红包；不为每堆创建红包 |
| 协议 | `RedPacketCreateData` / `BuildCreate` 包含一份 Def/材质/品质/耐久/状态模板、TotalCount、TotalPackets 和 PacketId | 同类等价状态资源不需要增加“来源堆数”字段。状态分片是传输同一份模板，不是多物品模板协议 |
| 入队 | `BuildInventoryBroadcast` 先准备状态分片及单条 create，relay.TryEnqueueBatch 提交整批；拒绝入队时回滚本地登记 | 入队成功不是远端领取成功；保留原确认和未知结果处理 |
| 领取 | `BuildRewardDeposit` 把 amount 记入库存，`CreateThingsFromTemplate` / `DeliveryCounts` 按接收端 stackLimit 拆分；TradeItemConverter.ConvertStatefulStackFromSnapshot 支持从总量模板恢复合法子堆 | 物理来源堆数不限制逻辑红包总数，实际交付仍受合法栈大小与批量上限限制 |
| 失败 | 取物异常恢复已弹出物，TrySendPacket 异常调用 RestorePoppedThings；库存来源用 reservation 恢复/核对 | 新来源计划必须全部复核后再取物，不能出现只取部分来源却按全部数量创建红包 |
| 返还 | 地图侧 ReturnRemaining 使用剩余 StoredThings，库存侧发送记录保存 Template/RemainingCount/UnsentCount，以稳定存入回执返还 | 多来源语义、剩余量和原状态必须一起验证，不能只测发送成功 |

## 支持范围与关键限制

### 1. 数量与逻辑红包互相独立

`TotalCount` 是物品总量，`TotalPackets` 是可领取份数。来源有几堆不决定红包份数。实现应只创建一个 PacketId，并保留用户选择的可领取份数，而不是强制把 TotalPackets 改成 1。

### 2. 单模板可表达等价资源，不能无损表达任意多个状态

当前 `PreparePhysical` 会把来源按完整状态分类，选择数量最多的状态作为模板，必要时从其他可堆叠状态补足数量。这意味着混合不同耐久/腐败进度/Mod 状态时，接收者未必获得各来源原有状态。

普通资源首批应优先复用能证明状态等价的来源，不按物品名字硬编码白名单，也不删除未知字段来制造相等。显示可以把资源归类；实际发送需要单独判定兼容性。若要明确允许状态归一化，或一个红包携带多份不同状态，就需单独讨论物品语义或协议，不能作为 UI 调整直接落地。

`Capture` 的严格状态校验与地图 `PreparePhysical` 的主模板策略当前并不相同，不能把库存多记录路径视为天然支持同一组合规则。

### 3. 库存多记录有接口基础，当前插件仍是单记录路径

现有 reservation 请求包含 Lines 列表，能表达多库存记录预留；但红包发送入口目前仅生成一条 EntryId 预留，并保存一份来源模板和未发送数量。可扩展为多条等价来源，但要完整验证原子预留、物化、提交、未发送部分返还与中断核对。

地图与库存混合来源同时含世界实物和持久预留，当前没有统一的事务/恢复记录。建议首批先完成地图多堆同资源，不把混合来源总量直接接到单记录或单来源发送入口。

### 4. 装备及特殊物品

按用户要求，武器/护甲/独立状态物品走单件路径；不能只依赖 stackLimit 判断所有物品类型，Mod 可能修改叠堆上限。普通资源仍需经过实际物品类别、可堆叠性、状态与数量复核。

### 5. 已有上限保持

目标数量是 int 范围；来源集合和交付拆堆存在 1000 堆保护，状态 payload 有尺寸限制，领取份数受现有明细上限约束。列表的 long 汇总不意味着可以无限制地发送。改动应提前显示具体上限和原因，不等到部分取物后才发现超限。

## 最小实施路线与验收

1. 调整浏览策略：装备/护甲保留单件，普通资源归类。将业务可发送总量与浏览汇总区分，来源刷新后旧草稿不得改指向别的物品。
2. 为地图普通资源生成一次多堆选择计划，连接既有取物、单红包创建与恢复链路。先完成状态等价资源，不增加协议字段。
3. 核验选取跨堆、最后一堆部分取走、部分来源被移动/消耗、序列化失败、取物失败、入队拒绝、领取拆堆、超时返还、关闭窗口及换存档。核对数量守恒和状态等价。
4. 库存跨记录、混合来源、不同状态合发分别评估；不能将上述首批通过扩写成全部支持。

## 已运行检查与限制

现有 source-linked RedPacketRepairTests 共 42 组通过，包括 3 堆各 75 选 200、来源原数量不变、模板包含总量、来源顺序与单足量堆优先、序列化失败恢复临时数量，以及接收端 200 → 75/75/50 的合法拆堆。夹具包含测试 serializer/Thing，并非实机化合燃料或石块，也不证明实际 Scribe、relay 服务与存档恢复端到端通过。
