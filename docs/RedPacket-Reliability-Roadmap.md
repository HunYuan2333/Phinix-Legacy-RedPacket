# 红包可靠性与容量 RoadMap

## RP-REL-01 — 可等价物品的紧凑库存记录（优先级：高；TODO）

**来源：2026-11-05 用户反馈。** 原木红包截图显示“物品 800000/999999 · 红包 8/10”；领取报错 `Red packet inventory delivery exceeds its stack limit`。截图数字不证明单次领取数量，复现时须记录实际 amount、物品 Def 和生效 stackLimit。

当前 `Client/RedPacketInventoryCodec.cs:BuildItems` 对有 StatePayload 的模板按游戏堆叠上限拆成 InventoryItem，超过 1000 条即失败。`RedPacketStateMachine.BuildRewardDeposit` 的 Def 缺失 fallback 为 stackLimit=1，也可能放大拆分量。异常使 relay cursor 保持重试，而固定容量错误不会因单纯重试消失。

用户要求：木头等能够证明等价的物品可以合并保存，避免为库存入账预先生成成千上万份相同模板。**本条仅记录后续任务，本轮不修改代码、协议或发布包。**

### 实施切片

1. **紧凑表示**：优先复用现有红包 codec/InventoryItem 的数量表达，让可证明等价的完整物品模板配合总数量形成紧凑库存记录；库存记录数与游戏地图合法堆数分开。不是把一个游戏 Thing 的 stackCount 强行改到超出其上限，也不是单纯提高 1000 条保护。
2. **等价判定**：原木是首个复现样本，不按 DefName 硬编码白名单。保留完整状态，核对 Def、材质、品质、耐久、腐败、样式、ThingComp 及其他有意义字段；只能按 codec 已证明的数量规则归一化，不能删未知字段来制造相等。不同状态分别记录，无法无损合并则明确说明限制。
3. **物化边界**：仅在提取或实际交付时按当前有效堆叠上限拆分，继续限制单次物化数量、内存及主线程预算。超大数量需要可恢复的分批方案；不能用“部分到账”冒充整笔领取成功，或在拆分异常后重复扣账/重投。
4. **幂等与兼容**：保持红包 ID、领取主体及 depositId 关联；完整持久入账成功后才推进领取处理。保持旧库存 payload、旧红包/发送记录及历史已提交存入收据可读可核对；格式/指纹变化不得让既有成功领取被当成未领取。是否需要 codec 版本迁移以实现试点结果决定，不预先更改协议。
5. **超限与队列**：发送前校验单次领取可表达性及接收预算，不能把固定超限当瞬时故障无限重试。Def 缺失要明确区别于真正的大数量。失败保留原消息、领取身份和未决证据，设计有边界的重试/提示；不能静默跳过领取、推进成成功或自动退款。

### 退出门槛

- 合成原木红包覆盖截图数量级（含 999999 总量及不同领取份额），记录实际领取量和运行时 stackLimit；普通等价原木入库不因预拆分超过 1000 条而失败。
- 覆盖堆叠上限 1/75/Mod 自定义值、恰好 1000 与 1001 堆、缺失 Def、不同物品状态、整数溢出和数量/载荷预算。大数量不意味着允许丢状态或无限分配。
- 新旧 payload 与已提交收据往返；重复消息、重连、保存/重启不重复领取，失败重试不提前扣除或丢弃合法数据。
- 保持库存真实事务及持久去重，验证入库后提取的数量/完整状态；分批物化中断和失败明确保留待核对结果。
- RimWorld 1.6/1.7 组件测试、各版真实游戏提取/存读档验收分别记录。紧凑库存记录或数据库条数不能证明真实游戏资产守恒。

### 依赖与范围

先在红包独立插件的 codec/领取边界做小规模试点，复用 Host 中立库存 API；只有现有合同确实无法表达时才提出中立合同增量及联合版本范围。第三方插件和红包保持平等，不在 Host 或 Server 添加红包专属分支。

既有发送侧归组设计继续参考 [多堆发送评估](RedPacket-Multi-Stack-Send-Feasibility-2026-10-17.md) 和 [随机来源模板策略](RedPacket-Random-Stack-Sending-2026-10-17.md)。发送侧已经采用的模板选择策略不等于允许接收侧丢弃字段；本待办不改其现有语义。
